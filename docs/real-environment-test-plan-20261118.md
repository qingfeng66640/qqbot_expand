四层分开记账：Service 返回成功不等于客户端展示成功；收到事件不等于 Chatter 已消费；离线100%覆盖不等于真实平台所有分支已测。

### 1.3 保留的边界

- 不以实机试验修复或压测框架既有并发 stop/start 竞态，只做**等待完成后的串行**停止与启动。
- 不给真实 QQ 注入伪造 Gateway 事件、畸形响应或伪造 Token，不在真实环境人为制造 401/5xx 来证明离线异常分支。
- 不进行暴力压测、配额耗尽、公开群广播、任意用户扫描或跨应用身份探测。
- `is_wakeup` 互动召回目前仅 raw 通道，没有专用召回策略，**不列入本轮必须成功项**。
- C2C 详细页的被动窗口存在60分钟/5分钟冲突；素材10 MB/10 MiB单位未对齐。这些只做有条件观察，不凭测试计划断言线上规则。
- HPACK 修复保护的是客户端、在途请求和响应流的日志寿命；不宣称重写了 httpcore 在部分关闭失败后的物理连接清理。该异常保留离线内存网络反例，不拿真实服务复刻异常池。

## 3. 配置档位：先最小，再按阶段打开

配置路径按当前文档为 `config/plugins/qqbot_adapter/config.toml`、`config/plugins/qqbot_expand/config.toml`；以实际部署加载路径为准。以下是**测试部署的局部配置片段**，不是可直接覆盖完整配置的文件；保留既有认证字段，不把秘密写进本方案。

### 3.1 Adapter最小档

```toml
[connection]
# 首轮沿用已核实的测试环境，不因404自动改production。
intents = 33554432

[features]
enable_c2c_message = true
enable_group_message = true
require_mention = true
group_list_type = "whitelist"
group_list = ["替换为G1真实group_openid", "替换为G2真实group_openid"]
private_list_type = "whitelist"
private_list = ["替换为U1真实user_openid", "替换为U2真实user_openid"]
ban_user_id = []
debug_log_raw_payload = false
debug_log_outbound_payload = false
enable_passive_reply_probability = false
streaming = false
markdown_support = false

[http]
retry_max_attempts = 0
```

**必须替换占位符且白名单非空。当前实现中空 `group_list/private_list` 表示不执行过滤，即使类型写了whitelist，也不是“拒绝全部”。** 这是本方案的重要安全前提。

Adapter名单主要是入站聊天过滤，不是所有非消息事件和所有Service出站的全局授权。受信测试调用方仍必须逐次核对固定目标；不能依靠这个名单阻止错误Service参数。

| 后续能力 | 需要的Intent组合 | 备注 |
| --- | ---: | --- |
| 群聊/C2C消息 | 33554432 | 默认bit25；平台是否投递普通群消息还受授权/接收设置限制 |
| 消息+成员增减/入群申请 | 50331648 | 加bit24；入群申请还要求Bot为管理员 |
| 消息+Interaction | 100663296 | 加bit26；callback使用 |
| 消息+成员+Interaction | 117440512 | 三位组合，必须有对应平台权限 |

只按已授权档位逐步增加，不从最大掩码起跑。设置了Intent不等于平台批准；拒绝后不要循环尝试不同掩码绕过授权。

### 3.2 Expand最小档

```toml
[features]
enable_tools = false
allow_raw_request = false
debug_log_payload = false
enable_group_info_service = true
enable_group_info_tools = false
enable_group_admin_service = false
enable_group_admin_tools = false
enable_group_members_service = false
enable_group_members_tools = false
enable_utility_tools = false
enable_material_service = false
allow_material_delete = false
enable_menu_panel_service = false
enable_menu_panel_tools = false
allow_global_menu_write = false
allow_panel_create = false
allow_panel_delete = false

[interaction]
enabled = false

[managed_panels]
enabled = false

[http]
retry_max_attempts = 0
```

首轮在两个插件都设置 `http.retry_max_attempts=0`，用于排除普通控制面操作的网络重试干扰；不要只改Expand，因为普通POST会委托Adapter。**0只关闭这类网络重试，不关闭Adapter普通POST独立的401刷新后重放。** 用户查询、专用@全体和素材一次性路径有各自不重放语义；不能把这些保证扩大到所有管理Service。普通管理写操作在正常凭据和稳定网络下每用例只调用一次；若你的测试规范要求“任何情况下最多一次物理HTTP”，本版本普通管理路径不满足该额外前提，应先阻塞该用例而不是修改私有传输。后续验证原网络重试配置时，仅在只读阶段恢复并另行记录，收尾恢复原配置。

用户查询通过公开 `qqbot_user_info` Service；不存在需要凭空添加的 `enable_user_info_service` 配置。即使禁用Tool，也不能推断Service或其他插件的主动行为全被禁用。

后续按用例单独打开：

- callback：**先核实并确认下述ACK固定基址例外，再**设置 `interaction.enabled=true` 和已授权bit26；不等于允许任何callback业务动作。
- 素材：`enable_material_service=true`；只在删除自己新上传的测试资产前设置 `allow_material_delete=true`。
- 管理只读/写入：对应 `enable_group_admin_service` 或 `enable_group_members_service`；每次由测试调用方限制G1/U2。
- Tool：最后才按需打开；群管理/成员Tool还需自己的非空 `group_admin_allowed_group_openids` / `group_members_allowed_group_openids`。
- 菜单/面板：只在专用测试App、备份和明确授权齐备后开启Service及相应写开关；托管自动对账另测，首轮不启用。

**Tool白名单不是所有Service的全局权限网关。** 受信Service调用者要自行实现“本次授权+固定测试目标”，不能以为Tool默认关闭就没有副作用。

### 3.3 Interaction ACK的固定基址例外

当前 `services/interaction_service.py` 对ACK明确使用 `force_production=True`，不按Adapter当前base_url选路。当前sandbox与production常量都已统一为 `https://api.bot.qq.com`，因此这**不是声称会切换到另一台主机、另一个Bot或另一套凭据**；它说明不能仅凭配置写sandbox，就保证所有路径都受沙箱隔离，尤其ACK固定采用正式API基址。

在**开启interaction消费与bit26之前**，需人工接受：测试会对当前Bot收到的真实interaction_id执行一次PUT应答，使用固定正式基址，且不自动重试。该确认只覆盖测试互动应答，不扩大到正式群、其他Bot或其他业务写权限。若授权严格限定“只允许沙箱隔离请求”而不能接受此路径，E阶段和任何需要ACK的菜单/callback测试记 `BLOCKED_PERMISSION`，保持interaction关闭；不要修改私有传输来绕过。

### 3.4 启动方式

沿用你已建立的启动器/服务管理方式。源码部署的项目README入口是 `uv run main.py`；若现有venv已就绪且不希望触发依赖同步，可从项目根使用已有解释器：

```bash
.venv/Scripts/python.exe -B -X utf8 main.py
```

此命令会启动真实Bot，只由操作员在前置清单完成后运行。使用启动器时不要再另开第二进程。首次协议/隐私授权由人工阅读处理，不用环境变量自动跳过。启动失败先收集脱敏原因，不为测试自动安装依赖或修改核心。

## 4. 测试调用与观察方式

### 4.1 不要把测试建立在随机LLM回复上

结构化用例应由**已加载Bot进程内的受信测试入口**调用公开Service，例如你现有的管理员测试插件或框架内受控控制台。它至少应做到：

1. 只接受负责人U1；目标固定为本轮登记的G1/G2/U1/U2，拒绝自由输入任意OpenID。
2. 默认只读；每个写用例有独立的确认、次数预算和清理记录。统一的“开始测试”不能替代R3逐项授权。
3. 从 `service_api.get_service()` 获取Service，不导入另一插件源码，不访问token/provider/client私有字段。
4. 记录返回摘要、用例ID、目标别名、耗时和次数，不打印完整响应/个人资料/URL。
5. 任务用TaskManager；卸载时只取消本入口拥有的任务和订阅，不触碰其他插件任务。
6. 观察事件只读，不修改EventParams键集合、不返回STOP拦截正式业务。

**本方案没有创建这个测试入口，也没有假定项目已有 `/qqtest` 命令。** 独立启动一个普通Python进程后调用 `get_service()` 不能代替真实Bot中已注册的组件。没有受信调用/观察入口时，可以先做人工收发和客户端观察，但字段、限流和取消用例应记 `BLOCKED_HARNESS`，不能凭聊天截图判通过。

可直接迁入受信入口的只读调用片段：

```python
from src.app.plugin_system.api import service_api

service = service_api.get_service("qqbot_expand:service:qqbot_user_info")
if service is None:
    raise RuntimeError("测试前提不满足：用户信息Service未加载")
result = await service.get_user_info(registered_c2c_user_openid)
# 只断言类型/存在性或记录 error_type；不要 print(result)。
if result["success"]:
    assert isinstance(result["data"]["username"], str)
    assert isinstance(result["data"]["avatar"], str)
    assert type(result["data"]["allow_proactive_msg"]) is bool
else:
    assert result["data"] is None
    safe_category = result["error_type"]
```

### 4.2 三个证据面

| 证据面 | 收集内容 | 不足以证明什么 |
| --- | --- | --- |
| QQ客户端 | 时间、测试标记、显示结果、是否提醒/引用/撤回；脱敏截图 | 不能证明所有内部字段/限流/取消分支 |
| 框架消息/公开事件 | event_type、路由别名、必要字段类型与相等断言、事件计数 | 不能把未到达的字段填成预期值；不得持久化完整raw事件 |
| Service及诊断 | success、稳定错误分类、耗时、有效ID是否存在、可观察的物理尝试数 | success不等于客户端必显示；看不到尝试数时写“未观测”，不猜1次 |

观察Adapter最终框架Message：`message.extra["qq_user"]`、`message.extra["qq_group"]`。可用 `member_nickname` 作当前群显示，但不能要求默认LLM或全局联系人自动把它显示为全局姓名。

非消息事件观察：`qqbot_adapter.group_add_robot`、`group_del_robot`、`group_member_add`、`group_member_remove`、`group_join_request`、`interaction_create`。按真实订阅路径记录，不能用手工调用转换函数代替平台投递。

### 4.3 日志与个人数据

- 全程保持 `Expand features.debug_log_payload=false`；不要为了排查打开完整请求体日志。
- Adapter的两个debug配置目前只输出结构摘要，需要时可临时开启，但仍先审查实际日志，不把名字理解为允许保存raw。
- 不常开全部第三方DEBUG。隐私专项仅在独立测试进程、短时间、受控本地采集；不得把完整HTTP头/响应体抓取作为常规证据。
- Token、AppSecret、Authorization、auth_token、头像完整URL和个人资料不进入报告。脱敏检查在本地进行，只输出发现类别/数量，不把命中原文再次打印出来。
- OpenID/消息ID/素材ID的原值只用于本地关联与清理；公开记录用别名或带每轮随机盐的摘要。trace_id如确需给平台排查，应经授权单独共享。
- 建议原始受限记录在本轮结束后24小时内复核脱敏，7天内清除；可按你的既有留存制度缩短。配置备份中的凭据不打进共享附件。

## 5. 实机用例

### A. 启动、隔离与连通（必测，R0/R1）

### B. 用户资料、群作用域与新事件（必测；部分字段条件性）

### G. 群聊@全体（R3，单独授权，不能批量执行）

**前提**：所有群成员知情；G1为测试群；C07能成功查询bot_state；预先确认本群今日额度未被其他程序使用。群状态查询本身受白名单权限约束；只有返回 `member_role == "admin"` 才进入发送。

严格按顺序：

1. **G01本地确认门禁**：`confirm=False`调用一次，应失败且不发消息；`confirm=1`不能当True。正文只用普通测试文本。
2. **G02普通出口门禁**：通过普通send_text/Markdown尝试包含全体意图的测试正文（如`@everyone测试`），期望本地拒绝、真实POST为0；不要改用raw.request绕过。仍需在专用群和受信入口中执行此R2负例。
3. **G03非管理员门禁**：Bot仍普通成员时显式入口confirm=True，查询角色后拒绝，真实群通知POST为0。查询无权限则BLOCKED_PERMISSION，不冒充非管理员逻辑通过。
4. 群主按需将Bot设为管理员；再次只读确认真实admin，不依赖旧缓存。
5. **G04真实发送**：人工再次确认准确G1、正文与当天一次额度，调用 `send_group_mention_everyone(G1, "[RUN_ID/G04] 已获准的测试通知", confirm=True, markdown=False)` **一次**。
6. 分别记录Service是否取得有效message_id、客户端是否显示@全体、成员是否被提醒、实际发送次数；不能只看返回success。
7. **G05配额观察可选**：同一天第二次发送不是默认测试步骤。只有另获同意且明确接受错误后果，才用专用群验证平台日限额；不为“证明限额”反复尝试。

同一群同一自然日不要把文本与Markdown各成功一次列为必测。若要两种都作真实成功测试，另选已授权群/另一天单独安排；日期边界以平台判定为准，不设计午夜跨日自动脚本。

超时、取消、断网或无有效ID一律 `UNKNOWN_SIDE_EFFECT`：先查看客户端和平台记录，不自动重试、不降级普通消息、不换私聊补发。撤回通知也不能恢复“未打扰”或假定恢复日额度。

审批、禁言的精确参数以API参考及实际Service签名为准。禁言请求使用 `members=[{"op":"add", "member_openid":..., "mute_expire_at":...}]`，恢复用op=del；审批使用 `approve_join_request(group_openid, member_openid, "approve"或"decline", join_request_id=...)`。执行前使用当前事件ID，不从历史日志猜测目标。

| ID | 操作 | 预期/通过标准 |

| J02 | 专用测试进程可选短时依赖DEBUG观察：1次用户查询，再按预算做3–5次正常只读请求 | 不出现旧用户info路径/认证值；普通无关日志仍可见；结束关闭诊断。实际未发生HPACK淘汰时，只记有限观察，不宣称完整延迟分支通过 |
| J03 | 正常串行停止Bot，等待任务/网络清理完成，再启动，共3轮 | 无重复Gateway/回调/心跳；无残留本插件任务警告；新轮C2C/G1各1条仍正常 |

| J05 | 可选：只读查询恰好在途时取消调用，再正常查1次 | 取消传播，不自动重试，不影响其他所有者；请求已到平台时只保证本地取消语义，不声称服务端未处理 |
| J06 | 实验性C2C streaming如需上线，单独启用；start→两次递增全文update→一次end | 只在C2C；最终正文完整、state=done且is_done=True；无悬挂“输入中”；事件来源msg_id/event_id互斥 |
| J07 | 60分钟稳定性观察，每5分钟人工1次健康检查或已授权测试消息 | 无持续重连/任务增长、无重复发送，内存/句柄无持续无界增长；到时记录实际趋势而非“看起来正常” |
| J08 | 若观察期间自然发生Token刷新 | 无秘密日志、无并发多TokenManager、随后请求成功；若未到刷新时间则NOT_OBSERVED |

重要限制：

- 不在真实环境跑离线的内存HPACK/部分池关闭注入脚本，不在实机强制让连接关闭报错，也不为触发表淘汰连续打70次接口。
- 不在真实写操作途中拔网来验证“一次性”；@全体/移除/素材完成的未知结果由离线反例验证，真实发生则按停止流程处理。
- HTTP/2是否协商成功、依赖是否支持，在可公开观察元数据下记录；若实际HTTP/1.1，不能声称HTTP/2线上路径通过，也不为测试改私有池状态。
- 串行重启只能证明串行生命周期，不能拿三轮正常重启宣称框架并发stop/start竞态已解决。
- 自然Token有效期不一定在60分钟内到期；不修改真实expires_in或凭据来凑刷新通过。

## 6. 流量预算、时间安排与停止线

### 6.1 推荐预算

| 项目 | 首轮建议上限 |
| --- | --- |
| 用户信息查询 | 常规每秒≤1次；首轮常规合计≤10次；C10另获准后仅一批11次 |
| 群状态/成员/策略等控制面 | 默认至少间隔3秒；每接口≤20次/分钟，进一步服从平台实际更低限制 |
| 可见消息 | 同目标至少间隔10秒、合计≤6条/分钟；首轮每会话建议≤20条 |
| @全体 | 同群同自然日最多安排1次成功测试；失败/未知不自动再试 |
| 素材 | 1–2张小图，先记image_id再清理；不试配额耗尽 |
| 移除/黑名单/禁言/审批 | 每个动作仅1个明确同意目标，逐项执行 |
| 菜单/面板 | 1个本轮测试面板；全局菜单仅专用App、保存并恢复原值 |

这些是**本方案的保守测试预算**，不是声称QQ新增统一配额。当前归档另有群主动Bot级60/30 QPM、单关系20 QPM；C2C认证等级QPS/QPM和单关系限制。所有流量包含其他组件与失败重试；429出现时立即暂停该阶段，不自动退避循环把测试跑完。

### 6.2 推荐安排

- 第一轮基础闭环：A+B01–B06+C01/C05/C07+D01–D05，约60–90分钟。优先找路由、资料与普通收发问题。
- 第二轮业务能力：E/F及必要C08–C09，约45–90分钟，按实际权限跳过并登记，不强行开权。
- 第三轮高副作用：G/H/I03–I07，约30–90分钟，每项单独批准；无测试资源时不做。
- 第四轮稳定性与清理：J，至少60分钟观察；跨日@全体/长窗口试验另约时间，不算在当天必须完成项。

预计完整首轮约3–6小时，含等待与取证；不含平台权限申请和跨日观察。时间预算不是超时/性能SLA。

### 6.3 立即停止条件

以下任一发生，停止新调用并暂停相关阶段：

- 消息到错误群/用户，或白名单外有任何管理写入。
- Token/AppSecret/鉴权参数、完整私人响应出现在可共享日志/Tool输出。
- 一个用例意外重复发送/重复管理、出现自动降级补发或不明后台任务持续运行。
- R3返回未知结果、超时、取消后无法确认实际状态。
- 清理失败、U2无法解禁/解除黑名单、全局菜单无法恢复。
- 平台429、封禁/权限异常或持续鉴权失败；不自动换环境、换ID或绕开限制重试。
- 代码/配置在过程中被另一会话修改，导致运行版本不再可追溯。

处理顺序：停止新任务 → 阻止自动动作/必要时正常停Bot → 从客户端/平台核实真实状态 → 由群主处理已发生副作用 → 本地保存最小脱敏证据 → 定位与修复 → 重新冻结版本后仅重跑受影响链路。若凭据可能暴露，由凭据所有者按平台流程轮换，不在聊天里提交密钥。

## 7. 清理、恢复与完成判定

### 7.1 按资产登记逐项清理

1. 停止测试入口，取消并等待其TaskManager任务结束，注销本入口callback及事件订阅；不全局清理其他插件任务。
2. 从平台/客户端复核U2禁言、成员、黑名单、审批状态；恢复为测试前状态。移除成功不自动再拉黑；加黑成功不假定成员已经移除。
3. 只删除登记在本轮RUN_ID下的素材、面板和策略；未知结果先查，不盲删、不自动补偿。全局菜单按测试前快照整体恢复并查回。
4. 如B退群/重加，恢复正确管理员和平台权限；一条受控C2C/G1冒烟通过后再结束。
5. 恢复require_mention、别名、流式、Intents、Tool与各管理/素材写开关；还原到预定上线配置，而不是机械“全部开启”。
6. 关闭短时DEBUG采集，保护/脱敏证据，正常停止测试Bot。释放测试数据按既有留存制度执行，不删除原业务记录。

清理状态必须单独签字：功能测试PASS但清理未完成，整轮不能记“可上线”。代码回退不能撤销已发送通知、审批或移除动作，必须人工核实平台状态。

### 7.2 通过门槛

- **基础可用**：A、B核心资料/作用域、C01/C05/C07（若群查询在上线范围）、D正常收发与引用、J正常日志/串行生命周期均通过；没有误路由、泄密或重复副作用。
- **功能可上线**：准备启用的每项能力都有真实平台成功用例、适用权限/失败用例和客户端证据；权限阻塞的能力保持关闭，不能纳入“已实机通过”。
- **管理可上线**：额外完成G/H/I中拟启用的R3项及恢复演练，精确限定目标、Tool权限和确认链。只读通过不能给写能力背书。
- **整轮关闭**：清理完成；所有FAIL已处置，所有BLOCKED/NOT_OBSERVED有明确范围，剩余风险书面接受；变更后受影响测试已重跑。

高优先级失败：误发/误管理、身份串用、群昵称污染全局、秘密泄漏、自动重放未知副作用，任何一项都阻断相关能力上线。

## 8. 失败定位速查

| 现象 | 优先区分与定位 |
| --- | --- |
| 没收到GROUP_JOIN_REQUEST | bit24是否实际订阅、Bot是否admin、平台授权；callback注册不自动增加Intent |
| @机器人能收到、普通群消息没有 | 平台recv_msg_setting/普通消息权限与require_mention分开看，先确认真实事件是否到Gateway |
| C2C昵称是别名但平台昵称不同 | 本地别名优先属正常；检查qq_user.username，不要求显示名等于平台名 |
| 群昵称串到另一个群 | 检查group_openid及qq_user.member_nickname作用域、全局Person写入；这是阻断缺陷，不靠别名遮盖 |
| union不存在 | 先核实三方绑定与官方可选条件，不生成替代值、不拿user/member ID冒充 |
| 用户查询无好友关系 | 真实C2C user_openid、当前Bot、好友关系/传播延迟；40184001不等于allow_proactive=False |
| bot_state返回11253 | 平台白名单未开；即使Bot是群管理员也可能无API权限；停止@全体测试 |
| 40103011/40103012 | 移除成员操作权限开关，与HTTP401/Token失效不同；不轮换Token来“修复” |
| 2xx但success=False | 检查安全业务码，2xx可能仍有非零err_code；不要把原始message拿来决定重试 |
| 返回成功但客户端无消息 | 分开核对目标、客户端版本、消息类型、URL报备、审查/投递延迟与权限；不立即重发 |
| callback发出但点击没反应 | bit26、interaction开关、路由注册、唯一ACK所有者、permission及超时；顶层type11/12不等于按钮action.type |
| 卡片失败 | 区分msg_type=8/card与Ark模板，核对权限、URL及图片；不改成纯文本后算卡片成功 |
| 素材返回file_info/引用混淆 | Markdown素材URI与/files的file_info是两套协议，Bot/目标/TTL约束不同 |
| 串行重启异常 | 区分插件自有任务清理、外部进程残留和框架既有竞态；禁止并行点stop/start来凑复现 |
